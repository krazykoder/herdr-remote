# Decision Log — Projects and Session Pairs

**Date:** 2026-08-08
**Context:** `.workflow/07_dev_notes/2026-08-08_projects_and_session_pairs.md`
**Status:** Proposal — not yet promoted to `.workflow/02_architecture/`.

---

## D1 — Project key is the raw `cwd`, with no git resolution

A Project groups agents by code root directory and is explicitly distinct from herdr's own workspace concept, which stays on the snapshot as raw metadata (`workspace_id`, `tab_id`) and disappears from the UI. The key is `f"{host}:{cwd}"`, with `basename(cwd)` as the display label — the label already exists on the snapshot as `project`. Git resolution (`rev-parse --show-toplevel`, plus `--git-common-dir` to fold worktrees into their parent) was considered and rejected for v1: it costs a subprocess per unseen cwd and an SSH round trip per remote cwd, in exchange for correctness in two cases — agents started in different subdirectories of one repo, and `herdr worktree create` siblings — that we accept splitting for now. Label collisions between two Projects sharing a basename are resolved presentationally in the client by extending each label leftward one path segment until unique; the relay stays out of it. Revisit in Phase 5 if monorepo or worktree splitting becomes an actual annoyance rather than a theoretical one.

## D2 — Session Pairs are explicitly pinned and persisted, not derived from herdr layout

A Pair is two user-pinned agent panes recorded in `pairs.json` in `LOG_DIR`, alongside the existing `push_subs.json` and following the same load/save pattern. The alternative — deriving a Pair from any tab containing exactly two agent panes, with roles stored as herdr pane labels — carried zero new state, survived relay restarts for free, and was visible in the herdr desktop UI, but it cannot express a pair whose members sit in different tabs, different Projects, or on different hosts, which the architect/reviewer workflow wants. The cost of the explicit model is a state file that can outlive its panes, and pane IDs are reusable, so each member stores an identity fingerprint (`agent`, `cwd`, `host`) captured at pin time. Every poll revalidates it: a missing pane makes the pair `stale` and recoverable, a mismatched fingerprint makes it `broken` and un-transferable until re-pinned. Health is derived per poll and never persisted. That validation is the price of D2 and is not optional — without it, a pair can silently retarget a different agent.

## D3 — No auto-relay in v1; every transfer is human-initiated

Auto-forwarding a finished agent's output to its partner is the natural conclusion of the pair concept and will be wanted, but it is an unsupervised agent-to-agent loop over content that may have originated on the open internet, and it removes the only reviewer of that content — the operator. V1 requires a deliberate human action per hop: select text, pick an instruction, send. Destination is confined to the other member of the same pair, the payload is capped at 4000 chars and fenced so the receiving agent can see where quoted material ends, instructions come from a server-side preset table rather than free client text, and every transfer is audited. Auto-relay is deferred to Phase 5 behind a per-pair opt-in and a hop limit, and needs its own threat model before it is specced.

## D4 — `start_agent` is restricted to allowlisted agent names in already-discovered Projects

`herdr agent start` accepts `-- <argv...>`, so exposing it over the network is exposing command execution. The client therefore sends an agent name and a `project_id` and nothing else — no argv, no env, no path — and the relay resolves the `cwd` itself from its own discovered Project set. The name must appear in `HERDR_START_AGENTS` (default `claude,codex`). A `HERDR_START_ROOTS` variant that would allow starting agents in any repo beneath configured parent directories was rejected: it adds path traversal and symlink escape to the surface, and the constraint it removes is mild, since opening a repo in herdr once makes it a discoverable Project. Because the relay binds `0.0.0.0` and `HERDR_RELAY_TOKEN` is optional today, all four new write commands are gated behind `HERDR_ENABLE_WRITE_EXT`, defaulting to off, and the relay refuses to start when that flag is set without a token.

## D5 — Start prompts are three server-side IDs, with `none` a first-class choice

A newly started agent is seeded with one of exactly three role prompts: `architect`, `reviewer`, or `none`. The client sends the ID; the prompt text lives in a server-side `START_PROMPTS` table and never crosses the wire, for the same reason transfer instructions do not (D3) — a client-supplied seed prompt is an unreviewed instruction injected into a fresh agent holding the operator's credentials. `none` is not a fallback for a missing value but a real option, because starting a plain agent in a Project is the common case and should not require dismissing a role picker. Seeding cannot fire immediately after `herdr agent start`, which returns before the agent TUI accepts input; the sequence waits on `herdr wait agent-status <pane> --status idle --timeout 30000` before sending, off the event loop, since `run_herdr`'s 15s timeout is shared with latency-sensitive callers and must not be raised. A seed that times out returns `seeded: false` with the pane left alive rather than reporting a success that did not happen. The three keys are the frozen contract; the strings behind them are prompt-engineering copy, will be retuned often, and are **supplied by the operator, not the Architect or the Implementer** — the table ships with `<<TBD …>>` placeholders that behave as `none` and log a warning, and an optional `HERDR_PROMPTS_FILE` JSON override loads over both the start prompts and the transfer presets at startup so the real copy never requires a code edit.
