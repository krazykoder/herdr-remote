# Decision Log — Projects and Session Pairs

**Date:** 2026-08-08
**Context:** `.workflow/07_dev_notes/2026-08-08_projects_and_session_pairs.md`
**Status:** Proposal — not yet promoted to `.workflow/02_architecture/`.

---

## D1 — Projects are configured launch targets; grouping uses lexical cwd roots

Projects are trusted `HERDR_PROJECTS_FILE` entries: unique opaque `id`, label, absolute `cwd`, and configured host. They exist even when no agents run, so browser can render a Project and start an agent remotely without relying on discovered panes. Relay matches every live pane to a same-host configured root using an exact-or-descendant path-boundary test; overlapping roots resolve to longest match. Thus an agent started locally in herdr from configured root or any subdirectory is grouped under that Project. Unmatched pane remains visible under Other sessions. Git and symlink resolution are deliberately absent: lexical path matching is enough for v1 and avoids local subprocesses plus remote round trips. Browser sends only `project_id`; relay resolves cwd and host, preserving launch boundary.

## D2 — Session Pairs are frontend state, not relay state

A Pair is two user-pinned agent panes stored in this browser's `localStorage`, with a user-facing name, a display `role` per member, and an identity fingerprint (`pane_id`, `host`, `agent`, `cwd`). The frontend matches that fingerprint against each live snapshot before offering transfer; no match or duplicate bare pane ID disables the shortcut, so a reused or ambiguous pane is never silently targeted. Both members must share a host, because G7 is a live relay bug — `_poll_once:251` keys `pane_remote_map` on bare `pane_id` across all hosts, so colliding IDs already mis-route `send_text` today — and a pair that silently addresses another machine is the worst outcome this feature can produce; the constraint lifts for free once pane identity becomes `(host, pane_id)`. A pane belongs to at most one pair: allowing several makes "resolve the other member" ambiguous, and the fix, a pair picker in the transfer flow, adds a step to the one action the feature exists for. The relay stores no pair data, validates no pair data, and has no pair command or broadcast. This keeps pairing a UI convenience rather than a new backend domain. Another device shows the same clearly named agents and can create its own local pair. Cross-device sync is deferred: if it earns its complexity, relay will store one authenticated, last-write-wins frontend-preferences blob, while the frontend continues to own pair semantics.

## D3 — Every step is manual in v1; transfer is frontend copy-paste with no relay command

Moving text between paired agents needs no server-side machinery. The frontend already renders the selected pane and owns one composer, so transfer is: select text in its view, pick an instruction shortcut, switch to the paired pane, and prefill that composer with the composed payload. It stops there — prefill, never auto-send — and the user presses send, which reuses the existing `send_text` + `send_keys ["Enter"]` path untouched. The earlier design routed this through a dedicated `transfer` relay command with a server-side instruction preset table and pair-scoped destination checks; all of it is redundant once the composition happens client-side, and dropping it removes a command, a preset table, and a validation path from the relay. What survives from that design is the fence around the quoted region, because transferred content containing a line like `Proceed to implement` is otherwise indistinguishable from the operator's own instruction, and that hazard is independent of where composition happens. The security consequence of the move is that containment becomes structural rather than enforced — the operator selects the text and reads the payload before sending, which is a stronger check than any relay-side rule, but only because prefill-not-send keeps them in the loop. Auto-relay, the natural next step, is deferred to Phase 5 behind a per-pair opt-in and a hop limit; it is an unsupervised agent-to-agent loop over content that may have originated on the open internet, and it needs its own threat model before it is specced.

## D4 — `start_agent` is restricted to allowlisted agent names in configured Projects

`herdr agent start` accepts `-- <argv...>`, so exposing it over the network is exposing command execution. Client therefore sends allowlisted agent name and configured `project_id`, never argv, env, path, or host. Relay resolves cwd and host from `HERDR_PROJECTS_FILE`; unknown IDs are refused. This permits remote starts when no session exists without accepting arbitrary launch paths. Because relay binds `0.0.0.0` and `HERDR_RELAY_TOKEN` is optional today, `start_agent` is gated behind `HERDR_ENABLE_WRITE_EXT`, defaulting to off, and relay refuses to start when that flag is set without a token.

## D5 — Agents start raw; instruction shortcuts are frontend-side path references

`start_agent` runs the agent and stops. Nothing is sent to it: no seed prompt, no role instruction, no wait for readiness. An earlier design seeded a new agent with one of three server-side role prompts, which dragged in a `START_PROMPTS` table, a placeholder-vs-real-copy lifecycle, an `HERDR_PROMPTS_FILE` override, and a readiness problem — `herdr agent start` returns before the agent TUI accepts input, so seeding needed `herdr wait agent-status --status idle` at a 30s timeout, which outlives `run_herdr`'s shared 15s limit (`:166`) and therefore needed to run off the event loop. Starting raw deletes all of it: the relay's start path becomes a single `herdr agent start` call inside the existing helper, and there is no timeout to widen, no partial-seed state to report, and no prompt copy anywhere in the relay. The capability moves to the frontend, where the user presses an instruction shortcut button after the agent appears. Prompts are referenced by path — `@.agent/prompts/System_Prompt_2_Architect.md` — so the agent resolves the file itself and neither the relay nor the frontend ever carries prompt text; changing a system prompt is editing a file in the repo, not shipping a client. The starter shortcut set lives as a `const` in `web/index.html`, consistent with how that single-file app already carries its themes and key presets. The cost is that shortcuts do not follow the user to the Telegram or Swift clients; promoting the list to a relay-served resource is listed under Phase 5 and is additive when it is wanted.

## D6 — Ambiguous pane IDs are refused, not resolved

G7 is a live routing bug: `_poll_once:250-253` keys `pane_remote_map`, `known_panes` and `agent_cache` on bare `pane_id` while iterating every host, so when two hosts report the same ID the last one polled wins and `respond`, `send_text`, `send_keys` and `read_pane` write to wrong machine. Proper `(host, pane_id)` migration is Class C and unrelated to P1. P1 therefore recomputes colliding IDs and every pane-addressed command refuses rather than guessing. New-workspace starts remain safe because relay resolves host/cwd from Project config and needs no pane lookup; New tab and Split require live same-Project, same-host sources and therefore use the refusal guard. This fixes current misrouting, fails closed, is empty for single-host operators, and self-heals within one poll interval.

## D7 — Projects render in configured order and never reorder by activity

The client lists Projects in `HERDR_PROJECTS_FILE` order. Sorting by most-recently-blocked was considered and rejected: the primary surface is a phone, and a list that reorders itself while the user is reaching for a card causes mistaps on exactly the control that approves or denies an agent. Urgency is already served by the blocked-agent hoist at the top of the list, which is a separate section and does not move the Projects below it. Alphabetical was also rejected — it is stable but throws away the operator's own ordering for no gain, and the file is hand-maintained, so its order is intentional.

## D8 — Projects contain native workspaces and tabs; pairs contain agent panes

Project is the configured persistent launch target. Workspace and tab remain the existing herdr terminal layout and stay visible in the browser under their Project; `create_tab` stays as a layout-only control, with its remote-routing bug fixed. A Pair is frontend-only metadata linking two live same-host agent panes, regardless of their tabs or workspaces. Complete remote spawn belongs to one explicit Start session flow: New workspace (default), New tab in a selected Project workspace, or Split beside a selected Project agent. The browser sends only placement plus safe existing IDs; relay resolves every cwd, host, workspace, and tab itself. Empty workspace creation has no independent UI because it does not yield a pairable or interactive session.

## D9 — Roles name sessions; prompt shortcuts remain explicit

Start session has Role dropdown values Architect, Reviewer, and Agent, plus an agent dropdown sourced from relay's allowlist (default `codex,claude,pi`). Role allocates a same-Project label such as `Architect 1`; it is applied to the new pane and, for New tab, its tab. It does not seed or alter agent context. Prompt buttons instead insert explicit `@.agent/prompts/...` strings into multiline composer; user can edit and send. This keeps role naming instant and avoids prior readiness/wait/seeding machinery.
